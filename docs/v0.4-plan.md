# v0.4: Safe editing

**Date:** 25 October 2026
**Builds on:** `v1-plan.md` and `v0.3-plan.md`. Everything stays read-only unless a connection opts in, and even then only the edit endpoint can write.
**Budget:** the target was under 2,000 lines of app code (excluding tests). v0.4 came to 2,107, which the user accepted; the row side panel brought it to 2,133.

## Scope

1. **Opt in per connection.** The connection dialog has an "Allow editing" checkbox, saved as `editable` in `connections.json`. It's off by default, and the server refuses edits for a connection without it.
2. **Only tables with a primary key.** Views, and tables without a primary key, stay read-only, and the tab says why.
3. **Edit, insert and delete in the grid.**
   - Clicking a cell opens its row in a side panel (resizable, closes with × or Esc). Every field can be copied; on an editable table you type or paste values, use **NULL** (and **Default** on a new row), and **Save** (⌘/Ctrl+Enter) stages them. The panel is read-only for SQL results and other tables.
   - **+ Row** adds a new row at the bottom of the page. Columns left untouched get their default.
   - **Delete rows** marks the selected rows for deletion (pressing it again restores them).
   - Cells cut at 10 KB can't be edited in the grid, because the full value isn't loaded.
4. **Review before applying.** Pending changes are highlighted in the grid and listed above it (update: old → new, insert, delete), each with its own revert, plus **Discard all** and **Apply**. Nothing is written until Apply. Paging, sorting, searching or closing the tab with pending changes asks first.
5. **One transaction, all or nothing, with conflict detection.**
   - Every change runs in a single `BEGIN READ WRITE … COMMIT`. Any error rolls back all of it.
   - Updates match the row on its primary key **and** the original text of each changed column. Deletes match the primary key and every loaded column. If a row was changed or deleted since it was loaded, the change matches no rows, so the apply fails with a clear message and nothing is written.
   - Values are sent as text parameters cast to the column's type (`$1::numeric`), so NULL, `''`, `0` and `false` stay distinct.
6. **Extra confirmation on `prod`.** Applying on a connection labelled `prod` asks for confirmation, naming the connection and table.

## The read-only exception

Pools keep `default_transaction_read_only=on`. Every existing endpoint still runs inside `BEGIN READ ONLY`, and the SQL box can still never write. Only `Edit` in `db.go` opens a `READ WRITE` transaction. It writes only statements it builds itself: identifiers checked against the catalog and quoted, every value a parameter. The server checks the opt-in before it begins.

## Out of scope

Editing through the SQL box, editing views or tables without a primary key, bulk paste, undo after apply, and editing cells cut at 10 KB.

## API addition

```
POST /api/c/{id}/{db}/edit   {schema, table, changes: [{op: insert|update|delete, key: {col: text|null}, set: {col: text|null}}]}
                             → {applied: n}   or an error, and then nothing was applied
```

## Done when

- Editing a keyed fixture row changes only that row and the chosen columns (checked with `psql`).
- Insert, update and delete can each be reviewed, applied and verified by re-reading. An insert leaves untouched columns at their default.
- Reverting before apply leaves the database unchanged. The UI sends nothing until Apply.
- A forced error in the third of three changes (for example a bad value for the type) rolls back the first two.
- A concurrent update, made with `psql` between load and apply, makes the apply fail with "changed or deleted since it was loaded", and the other session's value survives.
- NULL, `''`, `0` and `false` round-trip distinctly through edit and apply.
- A table without a primary key (`public.logs`) and a view can't be edited, and the server refuses it too.
- With editing off (the default), the edit endpoint refuses. With editing on, the SQL box still refuses `DELETE`.
- A `prod` connection asks again before applying.
- `go test ./...` and CI pass, and app code stays about 2,100 lines (2,107 accepted; 2,133 with the row panel).
